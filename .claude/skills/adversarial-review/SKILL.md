# 敵対的レビューサイクル

作業ブランチの実装に対し、独立したレビュアー（`adversarial-reviewer` subagent）にレビューさせる。
指摘は鵜呑みにせず自分で検証し、修正した内容を同じレビュアーに再検証させる。

## 原則

- **レビュアーの指摘は仮説であって事実ではない**。必ず自分でコードを読んで裏を取ってから対応を決める。
- **却下は正当な選択肢**。誤検知や、このプロジェクトでは意図的にそうしている箇所は、理由を添えて却下する。レビュアーに迎合しない。
- **報告は短く**。ユーザーは長文を読み飛ばす。表と短い箇条書きで、指摘 → 検証結果 → 対応 が一目で追えるようにする。
- **修正は指摘ごとにコミットを分けて積む**。まとめて 1 コミットにしない。どの指摘に何をしたかがコミット単位で追えることが、再検証の入力になる。**push はしない。**

## 手順

### 0. 対象の確定（必ず最初にユーザーへ確認する）

まず現在の状態を調べる。

```bash
git rev-parse --abbrev-ref HEAD                        # 現在のブランチ
git status --porcelain                                  # 未コミット差分の有無
git log --oneline -5                                    # 直近のコミット
BASE=$(git merge-base main HEAD 2>/dev/null)            # 比較ベースの既定候補
git diff --stat ${BASE}...HEAD
```

調べた結果を 3〜4 行で提示し、`AskUserQuestion` で **レビュー対象を確認してから先に進む**。確認せずにレビューを開始しない。

提示する内容:

- 現在のブランチ名
- 比較ベース（既定は `main` との merge-base。`main` が無ければ `master` / `develop` を探す）
- 差分のファイル数・行数
- 未コミット差分があるかどうか

聞くこと:

1. **レビュー対象** — 既定は「現在のブランチ（`<branch>` の `<base>` からの差分）」。これでよいか、別のブランチ・コミット範囲・PR 番号を指定するか。
2. **未コミット差分がある場合のみ** — コミット済みの分だけをレビューするか、作業ツリーの変更も含めるか。差分が無ければこの質問は出さない。

ユーザーが最初のメッセージで対象を明示している場合（「このブランチ」「PR #12 を」「main との差分で」など）は、その指定を既定として提示し、確認は 1 回で済ませる。

修正はコミットとして積んでいくため、**開始時に作業ツリーが clean であることが望ましい**。未コミット差分を含めてレビューする場合は、修正コミットと元の変更が混ざらないよう、先にコミットするかスタッシュするかをユーザーに確認する。

### 1. レビュー依頼（ラウンド 1）

`Agent` ツールで `subagent_type: "adversarial-reviewer"` を起動する。`run_in_background: false`（結果を待って次に進むため）。

プロンプトに必ず含めるもの:

- レビュー対象の範囲（`git diff <BASE>...HEAD`、ベースのコミットハッシュを明記）
- ラウンド番号（`R1`）
- このブランチが何を実装しようとしたものかの **最小限の説明**（1〜2文。設計の言い訳や「ここはこういう理由で」は書かない。書くと敵対性が落ちる）
- 「指摘のみ。修正はしない」

**返ってきた agent 名を必ず控える。** 以降の再検証はこの名前宛に `SendMessage` で送る。新しく `Agent` を起動し直すと前ラウンドの文脈が失われ、再検証にならない。

**このラウンドを始めた時点の HEAD も控える**（`git rev-parse HEAD`）。修正コミットはこの上に積み、次のラウンドではこのハッシュから HEAD までの範囲をレビュアーに渡す。ラウンドごとに控え直す。

### 2. 指摘の検証（ここが本体）

指摘 1 件ごとに、自分でコードを読んで次の 3 値に振り分ける。

| 判定         | 意味                         | 必要な根拠                                                           |
| ------------ | ---------------------------- | -------------------------------------------------------------------- |
| **採用**     | 指摘は正しい。直す           | 問題が起きる経路を `file:line` で特定できた                          |
| **却下**     | 誤検知。直さない             | 指摘が成立しない理由をコードで示せた                                 |
| **対応不要** | 指摘は正しいが、今は直さない | 影響範囲が閉じている / 別課題 / 意図的な設計、のいずれかを説明できる |

検証で使う手段:

- 該当箇所と、その呼び出し元・呼び出し先を読む
- 可能なら失敗するテストを書いて再現させる（再現しなければ却下の強い根拠になる）
- 既存のテスト・型チェック・lint を流す

根拠が出せない指摘は「採用」にしない。**読んでいないコードを、指摘されたという理由だけで書き換えない。**

### 3. 修正とコミット

採用した指摘だけを修正する。

- 指摘された範囲を超えて周辺をリファクタしない
- 却下・対応不要にしたものは何もコミットしない

**1 指摘 1 コミットで積んでいく。** 全部直してから 1 コミットにまとめない。レビュアーは次のラウンドでコミットを 1 つずつ見るため、コミットの粒度がそのまま再検証の粒度になる。

指摘ごとに、次を 1 サイクルとして回す。

1. その指摘の修正だけを書く
2. その指摘に対するテストを足す（再現テストがあれば、それが通ることを確認する）
3. テスト・型チェック・lint を流す
4. コミットする

**積んだ途中のどのコミットでもテストが通ること。** 通らない状態を経由すると、レビュアーがコミット単位で確認できなくなる。

複数の指摘を 1 コミットにまとめてよいのは、次のどちらかのときだけ。

- 同じ行を触るため分けられない
- 片方だけ直すとテストが落ちる（型が通らない、など）

まとめた場合は、コミットメッセージに対象の ID をすべて書く。

**コミットメッセージ** — 件名はプロジェクトの既存の規約（Conventional Commits など、`git log` で確認する）に従う。そのうえで、本文の末尾に対応する指摘 ID を書く。

```
fix: 空配列を渡されたときに落ちるのを直す

要素数を見ずに先頭を参照していたため、空配列で undefined を
読み出していた。ガードを足し、空配列のケースをテストで固定した。

Refs: R1-01
```

**push はしない。** ユーザーが明示的に頼んだときだけ。

### 4. 再検証依頼（ラウンド 2 以降）

`SendMessage` で **ステップ 1 で控えた agent 名** に送る。含めるもの:

- **このラウンドで積んだコミットの範囲**（`<ラウンド開始時の HEAD>..HEAD`）と、`git log --oneline` の出力
- **コミットと指摘 ID の対応表**（1 行 1 コミット）
- 却下・対応不要にした指摘の ID と、その理由
- 「**各コミットを個別に確認**したうえで、前ラウンド指摘の解消判定と、修正によるデグレの確認をしてほしい」

対応表の形:

| コミット  | ID           | 内容                                  |
| --------- | ------------ | ------------------------------------- |
| `a1b2c3d` | R1-01        | 空配列のガードを追加                  |
| `e4f5g6h` | R1-04, R1-05 | 同じ行を触るため 1 コミットにまとめた |

コミットを見れば差分は追えるので、**メッセージに差分そのものを貼らない**。何を意図した修正かを 1 行で書き、判断はレビュアーに任せる。

レビュアーが却下理由に反論してきた場合は、その反論をもう一度自分で検証する。反論が正しければ採用に変える。正しくなければ根拠を示して押し返す。

前ラウンドの修正が生んだデグレを指摘された場合も、同じくコミットを分けて積む。前のコミットを書き換えない（`--amend` や rebase をしない）。レビュアーが見た履歴が変わると、どのコミットを確認済みかが追えなくなる。

### 5. 終了判定

次のいずれかで終了する。

- 未解消の指摘がゼロ
- 残りが severity `low` のみで、ユーザーが打ち切りを了承した
- **ラウンド 3 に到達**（上限。それ以上は収束していないので、残課題を列挙してユーザーに判断を渡す）

終了時、作業ツリーが clean であること（採用した修正はすべてコミット済み）を `git status --porcelain` で確認し、積んだコミットを `git log --oneline <最初のラウンドの開始 HEAD>..HEAD` で提示する。**push はしていないことを明示する。**

コミットをまとめたい（squash したい）とユーザーが言った場合のみ、まとめる。こちらから提案しない。

## ユーザーへの報告

各ラウンド終了時に、以下の形式で報告する。**この形式を崩さない。散文で長々と書かない。**

```
## R1 レビュー結果

指摘 7件 → 採用 4 / 却下 2 / 対応不要 1

| ID | Sev | 指摘 | 検証結果 | 対応 | コミット |
|---|---|---|---|---|---|
| R1-01 | high | `parseConfig` が空配列で落ちる | 再現テストで確認 (config.test.ts) | 採用 → ガード追加 | `a1b2c3d` |
| R1-02 | med | N+1 クエリ | 呼び出しは初期化時1回のみ | 却下 | — |
| R1-03 | low | エラーメッセージが不親切 | 指摘は妥当 | 対応不要（別課題に切り出し） | — |

コミット: 4 件（`a1b2c3d`..`h7i8j9k`）、push なし
テスト: 全 42 件 pass
```

- 表は 1 指摘 1 行。指摘の要約は 1 行に収める。
- 却下・対応不要は理由を必ず書く。ここが一番読まれる。コミット欄は `—`。
- 最終ラウンド後は、これに加えて 3 行以内の総括（何が直ったか／残課題は何か）を付ける。

## 状態の保持

セッションが長引く場合のみ、`.claude/review-state.md` にラウンドごとの表を追記して文脈の消失に備える。短いサイクルなら不要。作成した場合は、サイクル終了時に残すか消すかユーザーに確認する。
