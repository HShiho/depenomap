# スカッシュマージ

作業ブランチの差分を、対象ブランチ（既定は `main`）へ 1 コミットとして取り込む。

## 原則

- **承認なしにコミットしない**。コミットメッセージと取り込む内容を提示し、ユーザーの承認を得てから `git commit` する。
- **マージの前と後で検査を回す**。前で通ることは、マージ後に通ることを保証しない。
- **push は別の確認**。マージとまとめて実行しない。
- **作業ブランチを消さない**。削除はこちらから提案しない。ユーザーが言ったときだけ。
- **報告は短く**。何が 1 コミットになるか、テストが通ったか、push したかが一目で分かればよい。

## 手順

### 0. 状態の確認（先に全部調べる）

```bash
git rev-parse --abbrev-ref HEAD                  # 現在のブランチ
git status --porcelain                            # 未コミット差分
git log --oneline <target>..HEAD | wc -l          # 取り込むコミット数
git log --oneline HEAD..<target>                  # 対象ブランチが先行していないか
git diff --stat <target>...HEAD                   # スカッシュ後の中身
```

**対象ブランチが先行している場合は、そのまま進めない。** スカッシュマージ自体は可能だが、その先行分を取り込んでいない状態でまとめることになる。先に `merge` か `rebase` で追いつくかをユーザーに確認する。

**未コミット差分がある場合も進めない。** マージの結果と混ざる。先にコミットするかスタッシュするかを確認する。

### 1. 検査コマンドの発見と実行

プロジェクトの検査コマンドを**推測せずに調べる**。

```bash
cat package.json | grep -A 20 '"scripts"'    # Node なら
ls Makefile justfile Taskfile.yml 2>/dev/null
```

見つかったもの（`test` / `lint` / `type-check` / `build` / `format:check` など）を**マージ前に全部回す**。1 つでも落ちていたら、その時点で止めてユーザーに報告する。落ちたままマージしない。

ランタイムが直接 PATH に無いことがある（`direnv` / `nvm` / `mise` / Nix devShell など）。`command -v` で確かめ、必要なら各コマンドの先頭で環境を読み込む。

### 2. コミットメッセージの作成

**既存の規約に合わせる。** 推測せず `git log` で確認する。

```bash
git log --format='%s' -10                    # 件名の書式（Conventional Commits か等）
git log --format='%b' -5                     # 本文・trailer の有無
```

- 件名は既存の書式に従う
- 本文には「**何を実装したか**」と「**なぜその形にしたか**」を書く。差分を読めば分かることは書かない
- 取り込むコミットの羅列にしない。スカッシュした時点で個々のコミットは履歴から消えるので、**残すべきは決定とその理由**
- `Co-Authored-By` などの trailer は、既存コミットが使っていれば付ける。使っていなければ付けない

### 3. 内容とメッセージの提示

コミットする前に、次を提示して承認を得る。

- 取り込むコミット数
- `git diff --stat` の要約（ファイル数・行数。全ファイル列挙が長ければ種別ごとにまとめる）
- 検査の結果
- コミットメッセージの全文

**ここで止まる。** 承認を得ずに次へ進まない。

### 4. マージとコミット

```bash
git switch <target>
git merge --squash <branch>
git status --short                            # ステージ内容を確認
git commit -F <メッセージファイル>
```

`--squash` はコミットせずステージに載せるだけなので、**コミット前にもう一度ステージ内容を確認できる**。想定と違えば `git merge --abort` ではなく `git reset` で戻す（`--squash` はマージ状態を作らない）。

コミットメッセージは `-m` を並べず、ファイルに書いて `-F` で渡す。改行と本文が意図どおりに入る。

### 5. マージ後の検査

**同じ検査をもう一度回す。** 対象ブランチ側に別の変更が入っていれば、ここで初めて落ちる。

あわせて確認する。

```bash
git status --porcelain                        # clean か
git log --oneline -3                          # 履歴の形
git log --oneline <upstream>..HEAD | wc -l    # 未 push の数
```

### 6. push の確認

**ここまでで一旦報告し、push するかを別に確認する。**

聞くこと:

1. **対象ブランチを push するか**
2. **作業ブランチも push するか** — スカッシュすると個々のコミットは対象ブランチの履歴から消える。作業ブランチを push しておくと、経緯（何をどう直したか）がリモートに残り、対象ブランチを巻き戻したときの退避先にもなる

push する場合、どのリモートのどのリポジトリに送るかを明示してから実行する。

### 7. 作業ブランチの扱い

**削除を提案しない。** スカッシュマージでは git が「マージ済み」と認識しないため `git branch -d` は拒否され `-D` が要る。個々のコミットは対象ブランチに残らないので、消すと経緯が失われる。

ユーザーが削除を求めた場合のみ、その旨（`-D` が要ること、経緯が消えること）を伝えてから実行する。

## ユーザーへの報告

### マージ後（push 前）

```
## スカッシュマージ完了

<n> コミット → 1 コミット（`<hash> <件名>`）

検査: test <n> 件 pass / lint / type-check / build / format:check 全通過
ワークツリー: clean
未 push: <target> が <n> コミット先行
```

### push 後

```
push 完了。<branch 一覧> が origin と同期。
```

- 差分の全ファイル列挙はしない。種別ごとの要約に留める。
- 検査が落ちた場合は、落ちたコマンドと出力の末尾だけを出す。

## 注意

- **`git merge --squash` は `--squash` を付け忘れると通常のマージになる。** マージコミットが作られ、履歴の形が変わる。実行前にコマンド文字列を目視する。
- **`-m` でメッセージを渡さない。** `--squash` の後の `git commit` は `.git/SQUASH_MSG` を既定のメッセージとして拾う。`-F` で明示的に上書きする。
- 対象ブランチが保護されている（force push 不可、直接 push 不可）場合は、スカッシュマージではなく PR を作る運用になっている可能性がある。`git log` に merge コミットが並んでいたら、その運用を確認する。
